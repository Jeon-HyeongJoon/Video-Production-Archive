# 14. 아카이브 작업 공간 UX·UI 설계 기준

상태: 초안 (2026-11-01). 0~1단계 기준서와 2단계 기능 분류까지 담는다. 확정 전까지 현재 화면 계약은 [09. 아카이브 작업 공간](09-archive-workspace.md) §7이 소유한다.

## 1. 목적과 진행 방식

지금까지 아카이브 작업 공간는 요청 하나마다 화면을 고치고 요구사항·golden·문서를 함께 바꿨다. 같은 날 막대 매트릭스 유지 결정이 흐름 그래프로 뒤집히는 등 결정 비용이 컸고, 기능이 한 화면에 계속 쌓였다. 이 문서는 먼저 제품의 기능을 대분류·중분류·소분류로 나눠 수준별로 정리하고, 그 분류를 묶어 메뉴와 화면으로 표현하기 위한 기준이다. 메뉴는 기능 분류의 결과이며 분류보다 먼저 정하지 않는다.

진행 순서는 다음과 같다. 각 단계 끝에서 담당자가 결정하고, 결정은 한 번에 하나씩 받는다.

| 단계 | 내용 | 산출물 | 위치 |
|---|---|---|---|
| 0 | 현행 정리 | 결정 목록과 유지·재검토 판정 | 이 문서 §7, §10 |
| 1 | 기준서 | 사용자·환경·규모·업무·원칙·성공 기준 | 이 문서 §2~§6 |
| 2 | 기능 분류 | 대분류·중분류·소분류 기능 목록과 소분류별 유형·주체·빈도·현재 상태 | 이 문서 §8 |
| 3 | 묶기와 메뉴 | 분류를 묶은 메뉴와 화면 목록, 화면마다 담을 소분류 | 이 문서 §9 (분류 승인 뒤) |
| 4 | 시나리오와 화면 상태 | 시나리오 6~8개로 메뉴·화면을 따라가 보고 상태 목록 작성 | 이 문서 |
| 5 | 와이어프레임 | 화면 상태별 저충실도 화면과 레이아웃 대안 | 디자인 캔버스 |
| 6 | 디자인 시스템 | 토큰·신호·아이콘·컴포넌트와 상태 | 디자인 캔버스, `static/style.css` |
| 7 | 시안과 검증 | fixture 데이터 시안, 시나리오 수행·접근성 점검 | 디자인 캔버스 |
| 8 | 확정과 구현 | 승인 묶음의 요구사항·테스트·golden·문서 반영 | `requirements/`, 코드 |

탐색은 캔버스에서 싸게 하고 확정은 묶음 단위로 한 번에 한다. 7단계 승인 전까지 아카이브 작업 공간 화면 코드는 버그 수정만 한다.

## 2. 사용자와 환경

2026-11-01 담당자 확인 내용이다.

- 사용자는 6~10명이다.
- 내부망 웹 아카이브 작업 공간를 띄워 두고 본다. 데스크톱 브라우저만 쓰고 휴대폰은 쓰지 않는다.
- 화면 밖 알림은 두지 않는다. 필요해지면 웹 화면 안에서 해결한다.

여러 사람이 같은 드라이브와 같은 보류를 동시에 본다. 낡은 화면에서 보낸 조작은 이미 revision 검사로 거부된다(`CMD-002`). v1은 로그인 없이 모든 요청을 단일 internal-operator로 처리하므로(`NET-002`, [06](06-archivist-security.md) §5) 누가 판정·시작했는지 사람별로 남기지 않는다(결정 7). 화면은 조작 주체를 담당자·Archivist·시스템으로만 구분한다.

## 3. 원본 규모와 업무 특성

| 원본 | 용량 | 내용 | 업무 특성 |
|---|---|---|---|
| 이동식 매체 (USB·SD card) | 32~128GB | 최근 촬영물 | 자주 들어오고 짧게 끝난다. 처리 뒤 매체를 다시 쓰므로 매번 원본 정리 판단이 따른다. |
| 기존 하드디스크 | 3~10TB | 1년치 매일 영상 기록물과 촬영물 | 폴더가 수백~수천 개(추정), 영상이 수천~수만 개(추정)이고 처리가 여러 날 걸린다. |

하드디스크 규모 때문에 다음이 필수다.

- 폴더 목록은 평면 목록으로 버틸 수 없다. 날짜·월 묶음, 상태 필터, 검색이 필요하다.
- 여러 날 걸리는 아카이브 실행에서는 폴더 수보다 영상 수나 용량 기준 진행이 체감과 맞을 수 있다.
- 화면을 오래 띄워 두므로 정상 상태는 조용해야 하고 문제만 눈에 띄어야 한다.

## 5. 설계 원칙

- **P1 원본 안전 우선.** 원본 정리 가능 여부는 시스템이 드라이브 단위로 판정해 한 곳에 보여주고 근거를 함께 둔다. 근거는 폴더별 보관 상태, 보류·실패 수, ArchiveCatalog 기록, 필요하면 STT와 아카이브 확정이다. 판정이 가능이 아니면 정리 관련 조작을 두지 않는다.
- **P2 평소에는 조용히, 문제만 드러낸다.** 단계별 진행 수와 병목은 문제가 있거나 사람이 찾을 때만 세부 설명으로 본다(2026-10-31 결정).
- **P3 한 화면에는 한 수준.** 전체 현황, 대상 목록, 대상 하나, 세부를 같은 높이에 섞지 않는다.
- **P4 화면은 업무 순서를 따른다.** 접수 → 처리 → 예외 → 정리 → 찾기.
- **P5 근거 있는 요소만.** 모든 표시 요소는 projection 필드·요구사항·표준 중 하나에 묶인다. 명사형 label과 추론 금지를 유지한다.
- **P6 규모에 견딘다.** 폴더 1,000개, 영상 10,000개 드라이브에서도 같은 화면 구조가 동작한다.
- **P7 여러 사람이 본다.** 결정과 조작은 시각과 행위자를 남기고 화면은 다른 사람의 변경과 Worker의 논리 드라이브 연결·분리를 5초 안에 같은 읽기 모델로 반영한다.

## 7. 현재 화면 기준

현재 구현은 작업 생성과 작업 관리를 분리한 사이드바 메뉴와 주소 가능한 route로 나눈다(결정 9-2, 결정 10~12, 결정 19~22).

기존 화면은 별도 legacy route나 전환 토글 없이 이 component 화면으로 직접 대체한다. 정적 shell에는 업무 데이터를 넣지 않고 모든 화면 상태와 조작은 same-origin `/api/v1` JSON API로만 연결한다. stable asset URL은 매 page load에서 다시 검증해 이전 화면 모듈과 새 component graph를 섞지 않는다. `DSH-034~035`

- 작업 생성: 영상 정리·보관 또는 기타 작업을 고르고 필요한 생성 입력만 표시하는 최상위 화면. 작업 상태 목록은 함께 표시하지 않는다.
- 작업 관리: 진행 중 ArchiveRun과 독립 Job, 시작 대기, 접고 펼치는 직접 확인할 항목·완료된 작업 목록. 한 행은 사람이 요청한 작업 하나(드라이브·첫 폴더 외 N개·요청 시각·흐린 작업 ID)이고 누르면 폴더별 작업이 펼쳐진다. `archive_run_id` 작업 화면(드라이브 개요·직접 확인할 항목·진행 중 폴더·하위 Job·저장된 결과·접힌 고정 범위)과 하위 `job_id` 상세
- 드라이브: 실행 전·처리 중·완료로 묶은 원본 드라이브 카드 목록, 드라이브 상세(연결·폴더 구조·영상 기록물·확인 필요·처리 이력)
- 장비·에이전트: 작업 PC 자원·Storage 접근, 논리 드라이브의 현재 연결·Worker·단계·결과 저장 위치, 에이전트의 실행 PC·실행 도구. online Worker의 현재 관측에서 빠진 영속 드라이브는 `연결 해제됨`, Worker가 offline이면 `확인 불가`로 표시한다.
- 상단 막대: 두지 않는다. 지금 위치는 상세 화면 제목 위의 경로 줄이 보인다.
- 사이드바: 맨 위의 보관 영상·자막 검색 칸과 아직 확인하지 않은 실패·직접 확인할 항목의 알림 버튼, 작업 생성·작업 관리·장비·에이전트 메뉴, 실행 중이거나 사람 결정을 기다리는 ArchiveRun 또는 독립 Job별 이름·상태 현재 작업 카드(작업 ID·드라이브·Worker는 마우스 오버), 아래 끝의 설정. 대기열·자원 대기·실패·완료 작업은 작업 관리에서만 다시 연다. 테마 전환은 설정 안에 있다.
- 전역: 본문 아래쪽의 새 직접 확인할 항목 토스트, 연결 끊김 한 줄 표시, 늘 오른쪽에 있는 Archivist 대화 칸(화면 표기 에이전트)

Archivist 대화 칸은 모든 화면의 오른쪽을 늘 차지하고 대화 기록은 칸 안에서만 scroll한다. 이 칸은 고른 테마의 작업 표면 색을 쓰는 둥근 패널로 본문에서 떨어져 있고, 사람의 지시는 말풍선, 에이전트 응답은 글줄, 실행 전 확인 필요 ActionCard는 둥근 카드로 둔다. 같은 ArchiveRun의 최초 지시와 SYSTEM 재호출은 구조화된 업무 문맥으로 묶으며, 실행 중에는 진행·Tool Call을 펼치고 전체 완료 뒤에는 최초 지시와 최종 보고만 남긴다. 실행 전 확인 필요 ActionCard는 접힘 밖에 둔다.

남은 화면 공백은 실패 재시도·범위 제외(B6.3)와 영상별 실패 이유(I2.2), 분류 확인에 쓰는 폴더 안 영상 목록과 기술정보(A2.2), 원본 정리 판정(E1), 아카이브 확정이다. 대량 폴더의 날짜·월 묶음과 가상화도 아직 별도 수용 검증이 필요하다. 390px 검사는 모바일 제품 범위가 아니라 문서 가로 넘침과 대화 칸 이탈을 막는 회귀 경계다.

### 7.1 작업 결과와 확인 순서

| 화면 | 처음 보이는 정보 | 펼쳤을 때 |
|---|---|---|
| 작업 관리 | 처리·시작 대기가 모두 0이면 직접 확인할 항목이 처음에 온다. 빈 두 목록은 0건 요약 한 줄로 합친다. | 해당 작업의 폴더, 원래 작업 ID와 상세 이동. 실패 폴더는 대기 수에서 빠진다. |
| 최근 실행·드라이브·장비 | 같은 ArchiveRun의 업무 결과, 범위 내 보관 폴더 수, 전체 발견 폴더 수. 처리 단계의 종료와 게시 성공은 독립된 기록이다. | 같은 폴더·Job·단계의 실패는 한 번만 표시하고 해당 기록에서 단계·오류 종류와 로그 참조를 확인한다. 에이전트 원인 확인은 실패 Job과 revision을 첨부한 진단 전용 요청이다. |
| 드라이브의 프록시 후보 | 발견 목록 전체의 후보 폴더 수, 대응 원본 수, 미확인 수. | 혼합 폴더를 먼저 연다. 미확인 근거가 있는 파일부터 보여 주며 전체 목록으로 전환할 수 있다. 파일명을 펼치면 해당 경로와 대응 원본을 확인한다. 분류 선택과 적용은 해당 실행의 보류 상세에서 담당자가 한다. |
| 에이전트 | 짧은 응답 또는 긴 보고의 첫 줄. 자동 지시는 자동 제안·점검 한 줄로 접는다. 실행 전 확인할 카드는 펼침 밖에 둔다. | 보고 전문으로 원래 응답을 읽고 처리 내역에서 도구와 근거를 추적한다. |

대시보드의 5초 갱신은 실행 범위와 상태를 계속 가져온다. 연결된 드라이브의 READY 발견 요약은 revision과 요약 내용 지문으로 비교해 바뀌었을 때 받는다. 영상별 근거는 폴더를 펼쳐 별도로 읽는다. 발견 근거와 실행에 첨부된 검사 결과는 해당 조회 범위에 맞춘다. 에이전트는 실행 상태 응답의 `work_state`로 결과를, `archive_run_state`로 처리 단계를 확인한다.

대응 계약은 `DSH-007`, `DSH-011`, `DSH-019`, `DSH-039`, `DSH-047~051`, `LRH-025`, `MCP-016~017`이다.

## 8. 기능 분류

기능은 메뉴가 아니라 제품이 하는 일 기준으로 나눈다. 대분류는 업무 목적, 중분류는 그 목적 안의 단계나 대상, 소분류는 화면에서 보거나 누르는 기능 하나다. 사용자에게 보이지 않는 내부 기능(Command Bus, lease, dispatch, 자원 예약)은 소분류에 넣지 않고 그 결과 상태만 소분류에 반영한다.

소분류 열의 뜻은 다음과 같다.

- 유형: 조회(보기), 조작(실행), 판정(사람이 결정하고 기록이 남는 조작), 설정
- 주체: 사람, Archivist, 시스템(자동)
- 빈도(추정): 상시(화면을 볼 때마다), 실행마다(아카이브 실행 한 번마다), 수시(문제가 생기거나 찾을 때), 드묾
- 현재: 화면(현재 화면에 있음), 일부(일부만 표시), API(API만 있음), 계획(planned 요구사항), 없음(요구사항도 없음)

### 8.11 전역 기능

대·중·소 분류와 별개로, 어느 화면에서든 접근하고 쓰는 편이 나은 기능을 따로 분류한다. 이 기능은 특정 메뉴에 속하지 않고 모든 화면에 공통으로 붙는 자리에 둔다. 레이아웃은 §8 분류와 이 전역 기능 분류를 기준으로 다시 짠다.

전역 기능으로 고르는 기준은 다음 중 하나다.

- 지금 보는 화면과 상관없이 알아야 한다. 다른 드라이브나 Worker에서 생긴 문제가 그 예다.
- 어떤 업무 중에도 끼어들 수 있다. 찾기와 Archivist 지시가 그 예다.
- 지금 보는 화면의 대상을 입력으로 쓴다. Archivist 지시의 선택 참조가 그 예다.
- 빈도가 상시다.

## 9. 묶기와 메뉴 구성 (분류 승인 뒤)

메뉴와 화면은 §8 분류가 승인된 뒤 다음 기준으로 소분류를 묶어 만든다.

- 같은 대상을 다루는 소분류는 같은 화면에 둔다. 대상은 드라이브 하나, 아카이브 실행 하나, 기록물 하나, 장비 하나처럼 projection이 가진 단위다.
- 업무 순서가 이어지는 소분류는 같은 흐름 안에서 끊기지 않게 둔다.
- 빈도가 상시인 소분류는 늘 보이는 자리, 수시는 한 번 이동, 드묾은 두 번 이상 이동해도 되는 자리에 둔다.
- 판정은 그 근거가 되는 조회와 같은 자리에 둔다. 보류 판정은 보류 사유와, 원본 삭제는 정리 판정 근거와 함께 둔다.
- Archivist가 할 수 있는 조작은 사람이 같은 결과를 확인하는 자리에서도 보이게 한다.
- 화면이 없는 소분류(없음·API·계획)는 묶기 전에 이번 재설계 범위에 넣을지 먼저 정한다.
- §8.11 전역 기능은 메뉴 안에 넣지 않고 모든 화면에 공통으로 붙는 자리에 둔다.

### 9.1 현행 화면 묶음 (2026-11-05)

§11의 결정 1·9·10을 반영한 현행 화면 기준이다. 아직 구현하지 않은 기능은 표의 범위에 남기되 상태를 계획 또는 없음으로 구분한다.

메뉴는 대분류를 그대로 옮기지 않고 영속 객체와 해결 위치를 기준으로 묶는다. A 접수·B 1단계·C 2단계·E 원본 정리의 드라이브 소분류는 주소 가능한 드라이브 상세 한 화면에 모은다. 작업 관리의 아카이브 단위는 담당자가 고른 원본·아카이브·고정 폴더 범위를 보존하는 `ArchiveRun` 하나이며 내부 검사·Folder·STT Job은 그 실행 상세의 하위 작업이다. ArchiveRun을 참조하지 않는 Job만 독립 상위 작업이다. 왼쪽 워크스페이스 카드는 새 객체가 아니라 미완료 ArchiveRun 또는 독립 Job 상세로 가는 탐색 projection이고 완료 작업은 작업 관리의 완료 목록에만 남는다. 모든 대상의 실패·사람 대기는 상단 알림에서 실제 해결 위치로 이동한다. Worker PC·논리 드라이브·Agent/Host는 연결 상태를 확인하는 대상이므로 연결 관리 한 화면의 독립 영역으로 모은다. C3 전사 결과는 대상이 기록물 하나이므로 검색 결과의 기록물 상세에 들어간다.

메뉴 이름과 순서는 작업 생성·작업 관리·장비·에이전트로 하고 Archivist는 오른쪽 대화 칸에 화면 표기 Agent로 둔다(결정 22, 2026-11-15).

# 기능별 안정성 검증과 배포 판정 제안

개발 단계에서 분류·폴더 매핑, FFmpeg·QC, 목적지 메타데이터, STT·자막, 아키비스트 에이전트의 품질을 각각 한 팀장이 맡는다. PM은 같은 입력이 다음 기능으로 전달된 뒤에도 결과와 근거가 일치하는지 확인하고 배포를 판정한다. 이 문서는 2026-11-25 개발 리비전 `ab840d3`의 품질 감사와 이후 배포 후보의 판정 기준을 정리한다. 현재 구현 상태와 테스트 소유자는 [요구사항 카탈로그](../../requirements/catalog.json)에서 확인한다.

## 1. 우선 막아야 할 실패

| 우선순위와 담당 | 확인한 현상 | 회귀 테스트에서 합격으로 볼 결과 |
|---|---|---|
| P0 · FFmpeg와 QC | 6초 H.264/AAC의 뒤쪽 영상 패킷을 손상시키자 FFmpeg가 정상 종료했다. 목적지 영상 트랙은 2.5초였지만 오디오는 끝까지 남아 QC 8개가 통과하고 보관 1건이 기록됐다. | 출력 영상 트랙의 끝을 **원본 영상 트랙의 기대 종료 시각**과 대조한다. 허용차 초과 시 기대·실측값을 남기고 성공 패키지와 카탈로그 행은 0건이어야 한다. 정상 파일과 허용차 안의 끝 프레임 손실을 대조군으로 둔다. `QCT-005` 관련 |
| P0 · 목적지 메타데이터 | v3 패키지의 정상 영상을 19바이트로 바꾸자 검증기는 손상을 발견했다. 이후 STT 게시 복구가 그 바이트의 해시로 리비전 2를 게시하고 카탈로그가 `CURRENT`가 됐다. | 복구 전에 이미 게시된 영상의 크기와 SHA-256을 직전 리비전의 기록과 대조한다. 바뀐 입력으로 두 번 복구해도 성공 출력은 0건이며 직전 manifest와 루트 CSV는 보존되어야 한다. 정상 대조군은 리비전이 한 번만 증가한다. `WRK-018` 관련 |
| P1 · 렌더와 작업 재시도 | 정상·손상·정상 순서로 검사와 분류를 통과한 세 입력에서 두 번째 렌더가 일시 장애로 끝났다. 첫 출력은 작업 폴더에 남았고 세 번째 입력은 시작하지 않았다. 다른 손상 샘플에서는 같은 입력을 세 번 실행했다. | 확인된 치명적 디코딩 실패는 첫 시도에 입력 ID·순번·마지막 위치·원인과 함께 기록한다. Control을 다시 열고 같은 입력의 후속 배정 0건을 확인한다. 경고 후 성공과 저장 장치 실패를 대조군으로 둔다. 정상 형제 파일의 계속 처리 또는 재개는 별도 업무 규칙으로 정한다. `WRK-022` 관련 |
| P1 · 분류와 목적지 매핑 | 규격이 다른 VJ 컷 두 개는 개별 게시에 성공하고 CSV에도 두 행이 생겼다. 게시 후 상태 조회는 존재하지 않는 `VJ.mp4` 한 경로를 돌려줬다. | 실제 Worker 게시 후 원본 ID별로 카탈로그 행과 저장소에서 다시 연 경로·파일 해시를 구하고, 같은 실행의 Archivist 조회와 대조한다. 합본이면 1개와 컷 순서·마커, 개별이면 실제 영상 N개가 일치해야 한다. `ORG-026` 관련 |
| P1 · STT 시간 검증 | 6,278ms 음성에 대해 엔진 대역이 7,900ms에 끝나는 구간을 반환했다. SRT와 TXT가 그대로 게시되고 카탈로그 검증도 통과했다. | 제안 정책은 음성 끝을 걸친 구간의 종료 시각을 실측 끝으로 제한하고 끝을 지난 구간은 제외하는 것이다. Transcript·SRT·TXT의 내용과 시각을 대조한다. 단일 청크와 청크를 합친 경우에 같은 기준을 적용한다. `TRN-002` 관련 |
| P1 · STT 문자 검증 | 엔진 응답의 잘못된 UTF-8 바이트가 대체 문자로 변환되어 품질 검사와 게시를 통과했다. | 원시 응답이 유효한 UTF-8인지 확인한다. 손상 응답은 `WHISPER_OUTPUT_INVALID` 근거를 남기고 새 전사 파일·리비전은 0건이며 기존 카탈로그가 보존되어야 한다. 정상 한글 대조군은 한 번 게시한다. `TRN-009` 관련 |

그다음 순서는 v2 패키지의 포인터 교체 직후에 장애를 일으켰다가 해제하는 복구, v3 원본 해상도와 CSV 필드 불일치, 파일명 하나에 VJ와 PGM 근거가 함께 있는 경우의 보류다. 구버전 패키지도 시험 대상에 포함한다. 새 분류 규칙에는 정상 대조군과 상충하는 근거를 가진 입력을 함께 둔다.

Windows 운영 조회에서는 검사 단계가 끝나고 렌더가 취소된 5개 입력의 상위 작업이 `COMPLETED`, 보관 결과는 0건이었다. 이 경우에는 실행 종료와 보관 성공을 각각 판정해야 한다. 운영자가 보는 결과 수와 Archivist가 설명하는 실패·중단 위치를 PM의 재현 시나리오에 함께 넣는다.

## 2. 팀장과 PM의 판정 범위

| 담당 | 고정할 시험 입력 | 완료와 성능을 판정할 근거 |
|---|---|---|
| 분류·폴더 매핑 | 행사 폴더 한 개에 VJ 컷, 녹화, 노이즈 후보, 근거가 충돌하는 파일을 둔다. 번호의 문자열 정렬과 촬영 순서가 다른 컷도 넣는다. | 고정 목록의 원본 ID, 판정·보류 이유, 20/6 Mbps 선택, 미리보기와 게시 후 실제 상대경로. 새 하드는 사람이 확인한 정답 표본으로 오분류·자동 결정·보류 건수를 따로 집계한다. 폴더 수와 검사 호출 수를 함께 기록한다. |
| FFmpeg·QC | 같은 짧은 영상의 정상, 말미 손실, 치명적 디코딩 실패와 정상 입력의 출력 쓰기 실패를 사용한다. 합본에는 색이 다른 컷을 순서대로 쓴다. | 실제 FFmpeg와 ffprobe 버전, 원본·출력 영상 트랙 길이와 프레임, 마커 양쪽의 재생 프레임, 기대 Profile과 QC, 재시도 횟수와 남은 임시 바이트. 같은 장비에서 미디어 1분당 처리시간을 비교한다. |
| 메타데이터·카탈로그 | 구버전과 현행 패키지, 원본·렌더 해상도가 서로 다른 한 쌍, 이미 게시된 영상 변조, 포인터 교체 중단을 사용한다. | 목적지 파일을 다시 열어 SHA-256·크기·기술정보를 확인한다. package ID별 리비전·루트 행·경로가 일치하고 재전송 후 중복이 없어야 한다. 대조 시간과 다시 읽은 바이트를 기록한다. |
| STT·자막 | 고정 음성·정답 문장, 침묵, 청크 경계를 넘는 발화, 잘못된 엔진 응답을 사용한다. 실제 한국어 품질은 운영 모델로 별도 측정한다. | 출력 시각·텍스트·UTF-8, 파일 해시, 카탈로그의 게시 리비전, 중단 후 재처리한 청크 수. 실제 모델에서는 문자 오류율, 누락 발화, 오디오 1분당 처리시간을 함께 기록한다. `TRN-003`의 대표 음성 인수 판정은 별도로 유지한다. |
| 아키비스트 에이전트 | 같은 실행에 대해 정상 보관, 확인된 원본 손상, 사용자 취소, 근거 누락을 질문한다. 승인 대기 중 세션을 재개하는 사례도 둔다. | 답변의 작업 ID·원인·결과 건수와 도구가 읽은 영속 근거를 대조한다. 근거가 부족하면 확인 범위를 설명하고, 사람 결정이 필요한 조치는 승인과 명령 기록까지 추적한다. 같은 사건을 올바르게 진단하기까지의 시간과 도구 호출 수를 기록한다. [아키비스트 설계](11-archivist-host.md) |
| PM · 기능 간 연결 | 하나의 고정 행사에 대해 정상 완료, 중간 입력 손상, 검증 후 게시 중단과 재시작을 재생한다. | 원본 ID에서 실제 영상·자막·메타데이터와 루트 행까지 추적한다. Control 재시작 뒤에도 작업 상세와 Archivist가 실제 결과 건수, 실패 위치, 재시도 가능 여부를 같은 근거로 설명해야 한다. 취소된 작업은 종료 상태·보관 수·미처리 수를 함께 검증한다. |

## 3. 실행 주기와 배포 판정

1. **변경마다 CI**에서 소유 요구사항의 주석 테스트 안에 정상·실패·재시도 사례를 둔다. 외부 도구의 반환값을 흉내 낸 사례로 예외 처리를 고정하고, 도구 간 의미가 바뀌는 경계는 작은 실제 파일을 생성해 끝까지 처리한다. 같은 실행에서 기존 `make verify`, `go vet ./...`와 운영 회귀 목록의 필수 사례가 실제로 실행됐는지 확인한다. [기존 증적 규약](10-capabilities-observability.md)
2. **배포 후보 리비전마다 Windows**에서 같은 리비전으로 빌드한 Control·Worker와 설치된 실행 파일·모델로 짧은 정상 경로와 해당 변경의 실패 경로를 실행한다. 기존 `APP-005`는 합본·마커·Worker 재시작을, `APP-007`은 녹화·한국어 전사·리비전 갱신을 담당한다. 가용 공간을 먼저 확인하고 지정한 시험 목적지 아래 실행 전용 폴더만 초기화한다. 원본은 읽기 전용으로 열고 전후 해시를 비교한다.
3. **운영 사고가 생기면** 입력의 최소 특성, 도구 버전·종료 코드, 마지막 정상 단계와 처음 틀린 관측값을 기록한다. 이를 재현하는 가장 작은 합성 자료와 정상 대조군으로 먼저 실패를 보인 뒤 수정한다. CI 근거와 같은 리비전의 Windows 근거를 연결해 사고를 종결한다.
4. **PM은 결과물로 배포를 판정한다.** 성공으로 보고한 영상의 실질적인 손실이나 손상 패키지의 정상 등록을 재현할 수 있으면 배포를 보류한다. 필수 사례의 실패·누락·스킵도 미검증으로 기록한다. 자료량을 늘리기 전에 고정 장비·도구·입력에서 지난 정상 리비전과 처리시간, 재시도 횟수, 임시 공간 최대치를 비교한다. 시간 허용치는 반복 측정해 편차를 확인한 뒤 정한다.

기존 요구사항의 의미를 보강하는 경우 해당 주석 테스트 하나에 하위 사례를 추가한다. 새로운 업무 동작이 필요하면 소유 설계, 관찰 가능한 Given/When/Then 하나, 요구사항 ID 하나, 주석 테스트 하나를 함께 검토한다. 장비 의존 동작은 실제 인수 근거를 확보한 뒤 상태를 올린다. [요구사항 운영 규칙](../../requirements/README.md)
